## 检索与阅读

沿用现有词项提取和进程内检索，不调用额外模型，不新增数据库或向量索引。评分从全文重复词频改为字段内词项覆盖：标题权重 4、标签 3、摘要 2、正文与 ID 各 1，同一词在同一字段重复不加分。这样避免长手册仅因重复通用词就压过对应主题；排序分数不是置信度。

通用聊天仍取 Top-3，Gateway 上下文预算不变；工具检索沿用原结果上限与权限边界。前端保留分类、原文预览和引用定位，本次没有实现 Markdown 富文本目录或文档内搜索。API 同时返回聚合 `content` 和结构化 `items`，兼容旧客户端。

手册标题说明问法另有保守路径：完整标题或开发者登记的 `question_aliases` 加有限说明后缀可以直接使用命中小节回答，不因选中业务项目就检查同名服务。该路径仅一次模型调用、无 Runtime 工具与历史现场信息，仍验证来源 ID；详见主设计 7.3。监控条目保留旧标题“Worker 不可用导致巡检停止”为别名，原条目 ID 不变。

路径问题定位、同模型三次复测与安全回归边界见 [手册问答耗时报告](../../test-results/14-system-handbook-latency.md)。

词法检索不具备可靠的语义拒答判定。无词项交集返回空；无答案问题若共享“参数”“规则”等词，仍可能召回相邻章节。不能将非空结果视为答案存在，本次未用任意分数阈值冒充语义相关性保证。最终答案正确性需单独评测。

## 事实与边界

- 默认 RabbitMQ 模式由 Maintenance 执行巡检、采集与过期恢复；原 Worker 仅在 PostgreSQL 回退模式兼任维护。
- SSH 挂载检查覆盖 Backend、Worker 与 Maintenance，不能只验收聊天连接。
- Redis 运行时降级与 Compose 新进程的启动依赖不同，空 `.env` 值也不一定禁用缓存。
- 登录 502、认证 401/429 与业务服务异常分开处理，代理故障不能通过重置账号解决。
- 内置知识是词法条目检索，项目文档另走数据库混合检索；未实现的四路径 Router、并行工具、自动学习规则不写成现有能力。
- 保留重排唯一来源条件、自动修复 development/test 限制、Action/Approval 与未知执行边界。
- README 负责产品能力、安装使用和必要限制；升级经过、实验与测量留在专项说明和 `test-results/`。

## 发布

应用在进程启动时加载定义。先确认无执行中的任务，再统一更新应用服务：

```sh
docker compose up -d --build backend worker outbox maintenance
```

登录后通过 `GET /api/system-knowledge` 或文档页应看到 12 份文档、84 个小节。检查 Backend/Worker 加载一致、旧引用可定位。定义更新不需要数据库迁移；本次没有前端代码变化，不必重建前端。
