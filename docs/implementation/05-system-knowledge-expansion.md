# 系统内置知识扩充

本次以 `34ac2d1` 后的当前工作区实现为依据。只扩充开发者维护的系统知识，不修改用户上传的项目资料。

## 组织方式

系统知识仍使用 YAML 保存可检索小节，由 Registry 将同一文件的小节合并成一份前端分类文档，不为每个错误生成单独 Markdown 文件。原有条目 ID 保留，以兼容历史回答引用。

| 分类文档 | 小节数 | 本次重点 |
| --- | ---: | --- |
| 系统功能与账号使用 | 4 | 能力与 Skill 边界、登录恢复、任务状态、证据引用 |
| 项目接入与文档管理 | 4 | 环境与连接、多项目区分、文档生命周期、上下文采集 |
| 部署、升级与维护 | 4 | 启动健康、网络位置、升级持久化、备份恢复 |
| SSH 连接与安全 | 10 | 首次接入、操作位置、主机指纹可信核验、运行时权限 |
| Docker 与运行时 | 7 | 原有故障加资源、依赖、端口与 daemon 排查 |

合计 8 份分类文档、51 个小节。命令示例是授权维护者的操作说明，不会给 Agent 新增可执行能力。

## 事实校正

- 删除“低于相关性阈值”作为现有无召回判断的描述，当前未部署实验中的相对分数阈值。
- 将重排触发说明改为唯一来源数超过结果上限，并说明开关和可用模型条件。
- 明确自动修复资格限于 development/test 的 docker_compose 停止服务；人工维护也可能满足停止判定。
- 明确系统知识采用词法条目检索，项目文档采用另一条数据库检索链路。
- 区分 API 审批决定与 Worker 执行消费，避免把本地防重等同于远程 exactly-once。

## 验证记录

实际运行了 `backend/tests/test_system_knowledge.py` 中全部 9 个测试函数，均通过，包括旧故障检索、新使用场景 Top-3、文档分组、只读标记与 ID 唯一性。

验证方式：宿主环境缺少 psycopg，因此用独立 Python harness 从现有 service.py 的 AST 加载原始 lexical_terms 函数，加载真实 Registry 和全部 YAML，执行测试函数。该方式隔离了数据库导入，但未替换分词和检索逻辑。它不是完整 pytest/API/数据库集成测试，也不是模型回答质量评测。

尚未验证：真实模型在新增语料上的问答正确性、全量 API 集成、重新构建部署后的页面操作。测试题属于已知功能回归，不应据此更新简历的盲测准确率。

## 发布方式

Backend 与 Worker 在进程启动时加载内置定义。需要构建并重建两个服务后生效：

```sh
docker compose up -d --build backend worker frontend
```

登录后打开文档页，应显示 8 份系统分类文档；打开一份应看到多个章节，历史有效条目引用仍可定位。之后用配置、账号、巡检范围和 SSH 指纹问题进行真实问答验收，并确认没有把说明文档当作当前运行状态证据。

## 旧版预览兼容修复

旧前端预览读取顶层 content，新分组 API 起初只返回 items，混合版本部署会造成有标题而正文空白。documents() 现在同时提供由原小节拼接的完整 content 和结构化 items，旧客户端可显示全文，新客户端保留章节定位。新增回归检查每份分类文档正文非空，且包含所有小节标题与原始正文。部署时应同时更新前端，并刷新浏览器；仅更新后端不会更新已有的前端资源。
