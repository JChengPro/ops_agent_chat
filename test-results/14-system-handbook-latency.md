# 系统手册问题误入运行时诊断：定位与复测

## 真实问题

问题：`Worker 不可用导致巡检停止 该怎么办`。用户在项目会话中提问，原 Run 为 `43d6ec81-2ae1-42de-a4d8-ef4b287268c6`，模型为 `qwen-plus`。

原回答把 Ops 巡检 Worker 与业务项目的视频处理 worker 混为一谈，读取业务服务状态、日志和 inspect 后宣称 worker 正常。该 Run 没有调用系统知识或项目 RAG，故此处延迟不能归因于知识库扩充。

| 阶段 | 耗时 |
| --- | ---: |
| Run 总耗时 | 36,682.270 ms |
| queue.wait | 93.491 ms |
| skill.selection（包含模型） | 3,584.956 ms |
| decision 第 1 轮（包含模型） | 10,367.869 ms |
| service.status / logs / inspect 合计 | 2,115.946 ms |
| decision 第 2 轮（包含模型） | 18,773.036 ms |
| answer.persist | 181.526 ms |

三次实际模型请求合计 32,496.308 ms，约占校正总耗时 88.6%，输入共 12,049 tokens。父阶段包含子请求，不应再次累加。原 UTC 墙钟区间为 33,967.318 ms，Profile 使用 Worker 单调时钟区间校正后为 36,682.270 ms；主机时钟跳变会影响跨进程计时，两个数都不等于浏览器实测。

## 修复范围

- 完整匹配内置手册标题或开发者登记的旧标题别名，并仅带有限说明后缀时，interactive Run 可选择 `system_handbook`。
- 沿用 `KNOWLEDGE_FAST_PATH_ENABLED` 开关。不是泛化关键词分类：实时请求、附加操作、含糊指代和监控自动诊断不进入此路径。
- 不选择 Skill，不提供 Runtime 工具，不携带项目历史，仅将匹配的公开知识小节交给一次回答模型。
- 模型明确区分 Ops 组件与业务项目同名服务，不声称完成现场检查；原引用过滤、取消检查、终态与持久化保留。
- 不修改模型、审批机制或项目 RAG 检索流程。README 仅说明该能力，实测放在本报告。

## 最终复测

相同问题、项目与环境，新建测试会话，经前端 Nginx 代理认证提交。模型仍为 `qwen-plus`，无运行时操作。观察时间采用 HTTP 800ms 轮询到 assistant 消息出现，不是浏览器渲染计时。

| Run | 服务端 ms | HTTP 观察 ms | 实际模型请求 ms |
| --- | ---: | ---: | ---: |
| `7c17378b-b689-45bf-9aab-928457d8b82d` | 5,043.851 | 5,810.028 | 4,602.651 |
| `90787802-e492-4b25-a2db-1887f34cf302` | 5,218.545 | 5,899.572 | 4,879.231 |
| `07d5f0eb-ee57-4a3c-8d87-f6ad36aa38f4` | 5,042.827 | 5,769.478 | 4,748.514 |

三次均 completed、一次 `general_response` 模型请求、759 输入 tokens、0 个 Action，引用 `monitoring_worker_unavailable`。服务端中位数 5,043.851 ms，相对该问题原基线减少约 86.2%。回答指出默认 RabbitMQ 模式由 Maintenance 巡检，postgres 模式 Worker 才兼任维护，并给出容器内配置检查及日志排查方式，未把业务 worker 正常当作 Ops 巡检正常的证据。

此前开发复测发现模型额外猜测“5–15 分钟”巡检间隔，另一次建议在宿主使用 `echo $TASK_BROKER`，会误读容器模式。已增加不补造参数和原文命令约束，并在手册明确 `docker compose exec -T backend printenv TASK_BROKER`。上表是这些修正后的结果；约束与三个正确样例不能证明所有模型输出都不会出现错误。

## 验证与限制

- 路由、项目知识快速路径、Agent 图、安全/API 与知识检索联合回归：140 passed、1 项既有 API 测试首次 401；该项单独复测 1 passed。未改认证逻辑，间歇原因未确认，不将联合运行描述成全绿。
- 最后调整回答约束和手册后，手册路径与内置检索专项 68 passed。覆盖混合变更不准入、自动诊断不准入、开关关闭、单模型无工具、伪造引用过滤及取消。
- 前端 `npm run test:e2e`、部署后 `/health` 和 `git diff --check` 通过。应用服务已重建部署。
- 初版性能脚本只等 Run 终态就读消息，曾先于 assistant 持久化得到空列表；最终复测等待该 Run 的 assistant 消息，不据此修改业务事务语义。
- 仅一个明确手册标题问题的三个样本，不是所有请求的延迟承诺或 P95。实时诊断仍可能有多轮模型和工具调用；一般口语意图路由仍有改进空间。
